Git & GitHub

Six short lectures on the tool every developer uses daily — Git to track versions on your machine, GitHub to share them with the world, and the dozen commands that cover 95% of real work.

What you'll be able to do after this lesson

  • Explain why version control exists — and what goes wrong without it.
  • Tell Git (the tool, local) apart from GitHub (the host, cloud).
  • Describe how distributed version control differs from the old centralized model.
  • Use the core vocabulary: repository, clone, commit, push, pull, fork, branch, merge.
  • Run the everyday loop: init, add, status, commit, push, pull.
  • Inspect history with log and diff, and collaborate with branches, forks, and merges.
  • Write commit messages a teammate (or future-you) can actually understand.
Reading Source Notes
Before you start

Install Git and make a free GitHub account. No notebooks in this module — everything below runs in a terminal:

terminal
git --version

If that prints a version number, you're ready. This page covers the module's notes end to end — the full source is linked above as Git_and_GitHub_Notes.md.

1The versions problem

Why version control exists in the first place.

Every beginner knows this folder: project.zip, project-final.zip, project-final-2.zip, project-FINAL-really.zip — four copies, no record of what changed between them, and genuine fear of deleting any of them. Multiply that by a team in different cities editing the same files, and you get lost work, overwritten fixes, and no way back.

The one-sentence version

Git turns "which copy is current?" into a question with an exact answer — the history log.

2Git vs. GitHub, centralized vs. distributed

Two names beginners always mix up — and the idea that makes Git special.

Git

A version control system — a tool on your machine that manages source-code history: tracking changes in files and reverting to a previous version when needed. Free and open source.

GitHub

A cloud hosting service for Git repositories — the place your repo lives so others can see it, copy it, and collaborate on it.

2.1 Why Git won: it's distributed

Old systems were centralized: one server held the history, and without a connection you couldn't do much. Git is distributed: the full history lives on every developer's machine — so you can work offline, commit whenever you want, and sync with the team later. It's also fast, free, and lets people in multiple locations work on the same project.

3Core vocabulary

Five words that unlock every Git conversation.

Repository

A directory where a project lives — local on your computer, or remote on a server like GitHub. It holds the project files plus each file's revision history.

Clone

A copy of a repository that lives on your computer instead of a server — and the act of creating that copy.

Commit

An individual change saved within Git (like saving a file, but tracked). Each commit gets a unique ID called a hash recording what changed, when, and by whom — with a short message describing it.

Push

Sending your committed changes up to a remote repository, e.g. on GitHub.

Pull

Bringing remote changes down into your local repository. When your copy is behind the remote, pull before you can push successfully.

Push vs. pull in one breath

Push = my commits go up. Pull = their commits come down. Keeping that direction straight keeps you out of most beginner trouble.

4First commands walkthrough

The everyday loop, in order — start a repo, stage, inspect, save, share.

4.1 Start: init or clone

terminal
git init

git init starts a new Git repository in the current folder. Joining an existing project instead? git clone obtains it from a URL:

terminal
git clone <repository-url>

4.2 Stage, inspect, save

Git only commits what you stage first. git add moves a change from the working directory to the staging area — telling Git to include it in the next commit:

terminal
git add <file>

Unsure what's staged? git status shows the state of the working directory and the staging area — which changes are staged, and which files Git isn't tracking yet:

terminal
git status

Happy with the staging area? git commit stores everything staged, with a message describing the change:

terminal
git commit -m "Commit message"
Two habits that pay off forever

Run git status constantly — it's a free X-ray of what you're about to save. And write messages that say why, not what: "Fix off-by-one in pagination" beats "stuff" for anyone reading the log later (including you).

4.3 Share: push and pull

terminal
git push

git push uploads your repository content to the remote. And git pull fetches content from the remote and immediately updates your local repository to match it:

terminal
git pull

5Collaborating: forks, branches, merges

How many people edit one project without stepping on each other.

Fork

A personal copy of someone else's repository in your account. Change it freely without touching the original — it stays connected, so you can propose your work back with a pull request and pull in their updates.

Branch

A parallel version of a repository that lives inside it. Work on a branch without disrupting the main line; merge it back when the work is done.

5.1 Seeing history and differences

git log lists the version history of the current branch, newest first. git diff shows what changed between the working directory and what's staged:

terminal
git log git diff

5.2 Branching commands

git branch lists, creates, or deletes branches; git checkout switches between them (or restores files); git merge joins histories back together:

terminal
git branch git checkout <branch-name> git merge <branch-name>
The collaboration loop in one breath

Fork their repo → clone your fork → branch for the feature → commit the work → push the branch → open a pull request. Every open-source contribution you'll ever make follows those six steps.

◐Wrap-up — Git in one breath

The whole module as a single pipeline.

the whole story
init / clone --> edit files --> add (stage) --> commit (save + message) --> push (share) --> pull (sync) --> branch / fork --> merge (reunite)
The one-sentence version

Git records every version of your project as a commit on your own machine; GitHub hosts those histories so a team can push, pull, branch, and merge them together — and a dozen commands (init, clone, add, status, commit, push, pull, log, diff, checkout, branch, merge) cover nearly everything you'll ever type.
